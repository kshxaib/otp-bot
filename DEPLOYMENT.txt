Render and mobile setup

1. Push this project to your own Git repository, excluding .env, *.session,
   *.db and __pycache__. Never upload your Telegram session or API secrets.
2. Create a Render Blueprint from render.yaml. It specifies an always-on
   starter service. Use one instance: the worker state lives in that process.
3. Enter TG_API_ID, TG_API_HASH and TG_SESSION_STRING as Render secrets.
   OTP_ACCESS_TOKEN is generated by the blueprint. Copy it from Render's
   environment settings into the extension Settings along with the HTTPS URL.
   If creating a service manually: build = pip install -r requirements.txt,
   start = python server.py, health path = /health. Set all four variables.
4. Reload/install the extension/ directory in a browser supporting unpacked
   Manifest V3 extensions and service workers. Reload existing website tabs.
5. Open the floating OTP panel, save the Render HTTPS URL and access token,
   select @Dark_Panel_83_bot and tap New Number. No next-button keyword needed.
6. The backend opens /start, Live Devices, each panel and its number batches.
   It reserves an unused Firebase number, opens it and refreshes SMS roughly
   every 3 seconds. Existing SMS form a baseline and are not reported as new.
   A new OTP is kept with its phone number in the last 20 results; the worker
   immediately continues. After 30 seconds without a new OTP it continues too.
7. Stop ends the server task. New Number replaces the current task and skips
   its already reserved number. Closing/minimizing the widget does not stop it.
   All tabs share one worker. Switching the displayed bot does not stop it.

The service must stay running: sleeping services cannot maintain the loop.
Server restarts/deploys clear OTP history and stop automation; press New Number
again. Firebase reservations remain. Exhausting available panels stops the
worker; press New Number later to scan newly available numbers.

Database/network failures stop the worker rather than accepting an unchecked
number. A number is reserved before opening its device; failed selections
therefore also remain used. Manual navigation is blocked while automation runs.
Avoid navigating the same bot in Telegram while it runs.

The dashboard prompts for OTP_ACCESS_TOKEN. Other API clients (including the
live-msg integration) must send Authorization: Bearer <OTP_ACCESS_TOKEN> when
the token is configured. The live-msg project was not changed here.

Validation uses simulated bot screens, not a live account. Actual button
layout and device availability must be checked with your authorized panel.
